# Process-local Python MLX cache diagnostic

The [request-aligned run](mlx-python-tail-gpu-v1.md) reproduced a Python batch-128 plateau with low reported global GPU utilization and a different range of global `In use system memory` values from later normal requests. The preceding Python comparison retained roughly 24 GiB in its MLX cache while Rust used a 4 GiB process-local limit. This motivates a controlled diagnostic, not an assertion that cache size caused the slowdown: an earlier Rust process also spiked with the 4 GiB limit.

The adapted Python benchmark now accepts optional `--diagnostic-cache-mib` and records the selected and previous process-local cache limits. The alternating runner accepts `--diagnostic-python-cache-mib` only with GPU activity sampling, labels the run diagnostic-only, and verifies each Python report's limit. With options absent, numerical operations and default Python cache policy remain unchanged. MLX describes this as a free-cache limit reclaimed on subsequent allocations, not a hard instantaneous memory cap. The unchanged performance gate still compares with the default Python policy.

Python syntax, existing observer/alignment/order tests, and rejection of missing GPU observation and out-of-range limits pass locally. Next check capped versus uncapped seed-42 codes and IDs on Mac, then run the same batch-128 request-aligned diagnostic at a 4,096 MiB Python cap and compare with the retained uncapped run. The runs are not paired under identical external activity, and monitoring can perturb timings; absence of a spike cannot prove a cause or a fix. No model, upstream pin, tolerance, GPU clock, global cache or system policy changes.
