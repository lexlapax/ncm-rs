# Isolated generator GELU fusion experiment

TinyStories applies GELU once per transformer block across 11 generated levels, or 132 times per request. This isolated experiment applies `tools/bench/phase4_generator_hybrid_norm.patch` followed by `tools/bench/phase4_generator_metal_gelu.patch`. For rank-three FP32 activations with width 3072 and batch at least 16, the patch computes the same exact-erf GELU expression in one custom Metal kernel; other shapes keep the existing path. The kernel uses checked element counts and row-contiguous inputs. Metal arithmetic may differ from MLX's composed expression, including for exceptional values; no parity or performance improvement is assumed. This is an experimental shape dispatch, not a production implementation or a claim that other profiles are qualified.

On Linux, the isolated copy passed formatting, the pinned CUDA Sudoku generator golden and strict-cuDNN TinyStories retained code/ID comparison using `cargo test -p ncm-backend-cuda --release --features cuda-cudnn --test generator_golden --test phase4_fused_norm_probe -- --include-ignored`; the Metal-only change leaves CUDA unchanged. The focused log `reports/phase4-gelu-metal-cuda-v1.log` has SHA-256 `0a5074fe201b1ebe3f831b1e7022ec0bf8cd27f80cbc2a49a15b65ea54874b65`. Patch replay reproduced the isolated source. These checks do not replace the full CUDA gate.

The first Metal build failed before any operator test: the kernel grid argument required `i32`, but the prototype supplied `usize`. The retained `reports/phase4-gelu-metal-mlx-test-v1.log` has SHA-256 `9190d4b997c00393674d9a8fd9bacbc5551de04d00c11ad1e2fe813a8936388e`. The revised `tools/bench/phase4_generator_metal_gelu_v2.patch` replaces that conversion with checked `i32` and `u32` conversions; its changes are confined to the Metal-only kernel and do not alter the CUDA code covered by the focused check above. The original patch remains available to reproduce the failed build.

The revised Rust build succeeded, but the focused Metal test failed when the runtime compiler could not resolve `erf` in the custom kernel source; `reports/phase4-gelu-metal-mlx-test-v2.log` SHA-256 is `64623d051a8a6e60d85554fa5cacd921901c7c4a90927f81e1dac9d9ca510ae9`. Pinned [MLX's unary implementation](https://github.com/ml-explore/mlx/blob/v0.32.2/mlx/backend/metal/kernels/unary_ops.h) includes its own [error-function implementation](https://github.com/ml-explore/mlx/blob/v0.32.2/mlx/backend/metal/kernels/erf.h); the custom-kernel source does not automatically include it. The handwritten kernel is deferred without a successful operator test or performance claim. Do not copy its upstream implementation or remove required license notices as a workaround.

An alternative is to evaluate MLX's existing shape-independent compiler on the generator's unchanged composed expression, building on the earlier [codec diagnostic](../2026-11-11-phase2-optimization/mlx-gelu-shapeless-result-v1.md). Any changed outputs require unchanged-reference numerical and quality evaluation. Full CUDA then Metal checks and source-bound Python quality/performance comparisons remain necessary before integration. A short screen cannot establish a remedy for the previous batch-128 tail.
