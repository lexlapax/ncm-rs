# Alternating-runtime GPU activity diagnostic

The [compiled-GELU Python comparison](mlx-generator-compiled-gelu-python-performance-v1.md) again had a long cluster in the second batch-128 Rust process. CPU top-process snapshots did not show high WindowServer CPU activity during that process; they do not show GPU contention. The prior [request-aligned GPU diagnostic](mlx-wall-gpu-diagnostic-v1.md) ran only Rust processes and did not reproduce the cluster. This follow-up adds device-wide GPU snapshots to the actual alternating Rust/Python workload and timestamps each Rust request. It tests a different observation method; it is not a performance gate or a claim that an outlier will occur.

Apply the hybrid normalization, compiled-GELU and wall-marker patches in order to an isolated checkout. The marked lifecycle example records timestamps but leaves model source unchanged; the compiled model source was byte-compared with the previously validated candidate. The repeated Python benchmark runner's optional `--gpu-activity` mode starts the read-only observer before work. For a subset of batches, its process order now follows the batch's position in the full matrix, so batch 128 alone retains the prior Python/Rust, Rust/Python, Python/Rust order. The default full-matrix order is unchanged. Local order, observer and alignment tests, syntax and help checks pass.

On available Metal hardware, build the marked example, then run only batch 128 with three alternating fresh processes per runtime, the existing lifecycle/cache settings and `--gpu-activity`. Analyze each marked Rust report using `tools/bench/analyze_phase4_gpu_activity.py` and preserve all outputs, including any absence of slow requests. GPU snapshots are system-wide with an uncalibrated averaging window, and last-submitter PID is not per-process GPU time. CPU sampling, timestamps and GPU polling may perturb execution. This diagnostic cannot establish causation or replace uninstrumented quality/performance gates.
