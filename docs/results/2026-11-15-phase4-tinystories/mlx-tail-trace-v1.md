# Marked TinyStories Metal tail trace

One bounded system-wide Metal System Trace was recorded around the isolated, signpost-instrumented batch-128 lifecycle diagnostic at an explicit process-local 4,096 MiB cache setting. The diagnostic used five warmups and 30 measured requests; its markers bracket each request and mark the return of `sample_seeded`. That marker is not a pure graph-construction boundary because sampling itself performs work and readback. The production checkout and model algorithms were not modified. Tracing can perturb execution and this is not a performance gate.

The measured median was 2,077.94 ms, p95 2,100.72 ms and maximum 2,107.12 ms; none exceeded four seconds. Consequently this capture does **not** contain the multi-second outlier and cannot identify its cause or show that it was fixed. It does not supersede the [failed paired comparison](mlx-cache4g-comparison-v1.md).

The trace contained two duplicate signpost streams. All 30 measured request intervals had consistent, ordered begin/sample-done/end markers; their durations matched the diagnostic's reported times within 0.00442 ms. The begin marker for the first warmup was absent, so the full 35-request marker sequence was incomplete. The exported GPU table had 29,411 target-process intervals; 25,200 overlapped measured request windows, with at least one overlap in each measured request. An overlap is not proof of causation or of all GPU activity. The local aggregate was produced by `tools/bench/analyze_phase4_mlx_trace.py`, whose 0.2 ms alignment check is a trace-timing check, not a changed model numerical tolerance. Synthetic complete-marker and missing-marker cases passed before the real export was analyzed.

The fixed 180-second recording completed, but Instruments continued actively saving. To prevent the original controller's 200-second post-target timeout from interrupting that live save, its owned controller process was temporarily paused after the target had exited and resumed once the recorder finished. This created a CPU-telemetry gap during post-workload saving; the trace result does not depend on continuous CPU telemetry during that interval. The capture script has since been corrected to wait for an active save without that arbitrary timeout. The raw system trace is approximately 2.4 GiB and, together with system-wide exports and activity, remains private on the Mac. Only target timing, capture metadata and the aggregate were copied locally.

The marked binary was built from isolated source at commit `9effe50`, with the checked patch and C shim linked explicitly; inputs and source hashes remained stable during capture. The result analyzer was commit `ea7aeb4`. The Mac could not reach GitHub for that commit after two attempts, so the already-pushed commit was fast-forwarded from a SHA-256-verified local Git bundle; both temporary transfer bundles were removed afterward. Target JSON SHA-256 is `8d2808f952179fa1fa2136ead291b3bb3986deac2706de1efb7a29ca49b0a382`, capture metadata is `a659e7b8e2077115050bb2804b0aded3c1c5a302920dd0c07917f661f2585312`, and the aggregate is `7484377eca7f62e025dbd1f04fca8db6484a36cadaa76b8927246f3805d45242`. The copied hashes matched the Mac originals. No repeat trace is implied by the absence of an outlier.
