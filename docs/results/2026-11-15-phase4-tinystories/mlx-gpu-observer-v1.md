# Read-only Metal activity observer

The optional `--gpu-activity` mode of `tools/bench/run_phase4_rope_ab.py` samples selected `IOAccelerator` registry fields using `/usr/sbin/ioreg`. Each record includes start/end monotonic and wall-clock timestamps, reported device/renderer/tiler utilization, reported allocated/in-use system memory and, when present, the last-submission PID. The observer starts before timed work, reports startup or sampling failures, and stores only the selected fields. Its sampling can perturb timing.

These values are **system-wide snapshots**, not per-process GPU time or a measurement of exclusive use. The meaning and averaging window of the registry counters and last-submission PID have not been independently calibrated. A reported PID does not establish that it caused a particular delay. CPU snapshots and any timing evidence still need their own limitations; no cause or fix for the existing tail is implied.

On Linux, four focused parser and observer tests passed, including malformed fields, whitelist behavior, readiness and error handling; the runner's syntax and help checks passed. On the Mac, a short read-only idle check collected three well-formed records without errors and without starting inference. The copied `reports/phase4-gpu-observer-idle-v1/activity.jsonl` matched the Mac's SHA-256 `9fb77b6339dc53e788c47623c173e7276e403e10aef2fbeee6c492f434fb743a`.

A separate six-second synthetic 2048×2048 FP32 MLX matrix-multiplication loop produced three samples: the reported device-utilization values were 0, 90 and 91, and the latter two last-submitter PIDs matched the test process. The copied `reports/phase4-gpu-observer-load-v1/activity.jsonl` matched SHA-256 `a49d2c46a45677a14b0a6cea4565ce144939fa12ee864a0919bacb2d157df12c`. This shows basic responsiveness for one controlled workload, not the sampling window, general PID attribution or integration with a real benchmark. An instrumented run is diagnostic and cannot substitute for an uninstrumented performance gate.
