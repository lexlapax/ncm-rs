# TinyStories CUDA sampling and layout exploration

This is an exploratory measurement, not an acceptance gate. Each Rust cell is a single fresh process with five warmups and 30 synchronized generation/readback trials on an RTX 3060 Ti. Before/after refers to generic versus specialized exact 12-head QKV layout. Both versions use an experimental SplitMix64 seeded inverse-CDF sampler; PyTorch uses its own random stream and multinomial implementation. The output sequences therefore differ. No formal stochastic quality comparison, paired randomized trial, or isolated activity qualification has been completed.

The pinned Python implementation at batch 4 recorded a 102.673 ms median and 2,498,456 KiB peak process RSS; Rust's generic-layout run recorded 100.187 ms and 1,118,548 KiB. Both used generation plus code and final-ID host readback; startup/model loading was excluded from the timings but included in whole-process RSS. This one pair does not establish a performance gate. Python used default PyTorch SDPA and TF32 was disabled. The native sampler avoids sorting the vocabulary at top-p 1, using inverse-CDF draws for the same categorical distribution subject to FP32 reduction and PRNG differences; those differences still require quality qualification.

The first Python batch-32 trial failed with CUDA OOM during upstream top-p sampling. A contemporaneous GPU query showed a separate `llama-server` using 3,232 MiB and other desktop GPU clients; total GPU usage was 5,030 MiB out of 8,192 MiB after the failing process exited. Thus no Python batch-32 timing or memory comparison is claimed. Rust batch 32 finished with 1,117,656 KiB peak process RSS for the generic-layout run under that activity. The failure and raw timings are retained in ignored `reports/phase4-tinystories-*` files.

The CUDA 12-head layout passed exact-value tests for four shapes, and the complete two-item teacher-forced and codec diagnostic summary remained byte-identical before/after (`bf6765fbba0ff6867652c595b926277ab25ac42d5cf6abd86ac7f93050aaa6f2`). Controlled CDF tests included uniform, nonuniform and invalid input rows; seeded real-checkpoint smoke tests checked reproducibility, different seeds and prefix rejection. These checks do not establish numerical or stochastic quality parity. The sampler reports invalid rows with a sentinel, and the generator checks all sampled codes before returning results. Apple implementation remains pending.

Five separate development seeds `[100, 101, 102, 103, 104]`, 128 samples each and generation batch 4, produced mean upstream token entropies of 3.976189 (Python, seed SD 0.009159) and 3.977341 (Rust, seed SD 0.009464). All 1,280 raw-ID/text/token triples were independently re-decoded and re-encoded with the pinned upstream BPE implementation before scoring. The seeds are outside the reserved official set. This is exploratory and does not include generative perplexity; no quality margin or gate pass follows. Raw inputs and entropy report remain in ignored `reports/phase4-tinystories-development-v1/`; the entropy report SHA-256 is `7f3f83768de0a0294e628bb01979161872a84b7caf1b3e16879193d86664d1eb`. Recompute it with `tools/reference/tinystories_quality.py --entropy-only` using both the `python-*.json` and `rust-*.json` sample files and the pinned evaluator/tokenizer paths.

These timings and development samples were collected before a subsequent sampler review found that the parallel FP32 prefix scan could produce nonmonotone boundaries at rare rounding ties. The implementation was changed to a fixed-order monotone scan with initialized error sentinel. These observations remain historical; remeasure timing and regenerate Rust development samples with the corrected sampler before using them to set a quality threshold.
