# TinyStories CUDA performance and memory comparison

Three alternating fresh processes per runtime and batch each ran five warmups and 30 synchronized generation trials on an NVIDIA GeForce RTX 3060 Ti. Each timed trial includes generation plus host readback of all codes and final IDs; model loading is excluded. Rust's sampled generation reads codes internally to reject invalid sampler results before decoding, and the benchmark reads them again. Python uses the pinned upstream generator and codec with PyTorch's default SDPA and TF32 disabled. Rust uses SplitMix64/inverse-CDF sampling; Python uses PyTorch multinomial. The implementations therefore generate different samples, and this comparison does not imply output identity. The separately scored stochastic quality result is [here](heldout-quality-v1.md).

Latency is the median of the three per-process medians; p95 is nearest-rank over the pooled 90 trials. RSS is the median GNU `time` whole-process high-water mark, including model loading. Under this test, Rust's median latency and peak RSS are lower at all four batches, with the smallest latency advantage about 3.3%. This satisfies the measured direction for these CUDA timing/RSS cells; it is not yet a full TinyStories runtime gate or a cross-platform claim.

The original Python benchmark OOMed during repeated batch-128 trials. Its live allocated GPU memory grew about 352 MiB per request even after all visible request outputs were explicitly released; additional diagnostics, including failed default/expandable-allocator/cache-clear attempts, remain in `reports/phase4-tinystories-python-b128-*-v*.{log,txt}`. Explicit Python `gc.collect()` after each request kept live allocations stable. For all Python cells above, collection ran **outside** the generation timing; its separate median was about 51–52 ms per request. This is a conservative compute-only comparison, not a claim that applications necessarily pay a full collection after every request. Both runtimes' process RSS includes startup and all cleanup.

The GPU monitor sampled `nvidia-smi` roughly once per second. Per-process sampled peak ranges across the three runs were Python/Rust 844/676 MiB (batch 1), 928/708 MiB (batch 4), 2386/1060–1188 MiB (batch 32), and 5964/2308–2820 MiB (batch 128). These are process-level samples, include allocator/context effects and can miss transient peaks; they are not interchangeable with exact PyTorch allocated/reserved counters or MLX memory metrics. GPU activity was not isolated: Chrome, 1Password, walker and t3code processes were present during all 712 telemetry samples. GPU clock observations ranged from 210 MHz at idle to 1965 MHz; no clock policy was changed. Additional CPU process snapshots cover part of the batch-128 runs; `ps` CPU percentages are process lifetime averages, not instantaneous utilization. These activity and sampling limitations remain material, especially for the small batch-128 latency margin.
