# XSum long-attention CUDA optimization

A bounded CUPTI trace of the previously measured Rust binary identified repeated full attention-score mask additions as a substantial cost. Across seven instrumented requests, it recorded 2,660 `badd_f32` kernels with 942.23 ms of summed GPU duration, alongside 763 softmax kernels and the matrix multiplications. Activity durations can overlap and the trace includes setup; these sums are neither request latency nor proof that every addition was an attention mask. The capture and summary are `reports/phase4-xsum-cupti-v1/capture.txt` and `summary.json`, SHA-256 `bef51b40cb467b16cf8a93a13e8ba6edaa653ba9e23cdb9ae60c428b01a59ba1` and `6da28e3252752c7e85367a4568585535e52a3a7abac330d41895ef229a0d85ff`.

For supported contiguous long-attention shapes, the CUDA backend now combines the existing width-64 scaling, additive broadcast mask and warp-wise softmax into one kernel. Other shapes retain the prior implementation. The reduction follows the operation order of Candle's `candle-kernels` 0.11.1 softmax, which credits [llama.cpp's ggml CUDA source](https://github.com/ggml-org/llama.cpp/blob/d59bd97065cd7ded6c4ecab54b1d5e0b1b11e318/ggml-cuda.cu); the [upstream MIT license](https://github.com/ggml-org/llama.cpp/blob/d59bd97065cd7ded6c4ecab54b1d5e0b1b11e318/LICENSE) and Candle MIT license are retained with the backend. No tolerance or model formula changed.

On real CUDA, the fused softmax matched the prior separate operations bit-for-bit for finite outputs across three shapes, with NaNs matching as NaNs for fully masked rows. A complete attention comparison was also bit-identical. The full XSum model matched the prior Python-reference summaries on the synthetic padded, real-passage and full-prefix cases: each retained all 400 checked codes and 96 final IDs, and the existing float diagnostic bands. Both traced and untraced generation agreed. These limited cases do not establish full-dataset quality.

`CUDA_COMPUTE_CAP=86 RUSTC_WRAPPER= tools/check.sh --cuda` passed on the final source, including both new real-device tests and 18 existing CUDA operator cases. Its log `reports/phase4-xsum-fused-attention-check-v2.log` SHA-256 is `095ef7a57539db2ca54d9c795b491c138bb3837502bd99c0a699634f76052385`. The first full attempt stopped in the unrelated CPU clock-restoration process-observer fixture with `ObservationMismatch`; that log's SHA-256 is `7d339d49365cc0d3ad82a47295ef97e6ee18c1364d65893c56d3ddca6f11579c`. The fixture passed unchanged in isolation before the successful full rerun; its underlying intermittent mismatch was not diagnosed. Ignored profile-specific tests are not implied to have run.

The repeated comparison in `reports/phase4-xsum-cuda-performance-v2/` used five warmups and 30 timed batches in each of three alternating fresh processes per runtime, with fixed inputs and synchronized output readback. Model load is excluded from latency; RSS includes the whole process and load. All generated codes and final IDs matched across processes and runtimes.

Rust is about 16% faster by median and uses about 43% less peak process RSS in both measured cells. The earlier slower Rust batch-4 result remains in the [prior report](cuda-device-selection-v1.md). Rust's CUDA default async pool reported used/reserved high-water marks of 632.73/672 MiB at batch 1 and 785.61/896 MiB at batch 4, with 608 MiB reserved after requests. These pool counters include load and exclude allocations outside that pool. Python reported allocator allocated/reserved peaks of 973.03/1,006 MiB and 1,718.22/1,864 MiB respectively; the allocator scopes differ and the numbers are not direct device-wide comparisons.

All 191 activity samples returned both GPU queries. Four nonbenchmark GPU processes appeared throughout, with 307 MiB collectively reported; global utilization ranged 0–100% and SM clocks 210–1,965 MHz across the wider run. There is no process-attributed utilization, so interference remains possible. The benchmark manifest and activity SHA-256 values are `38f4ba4c55e5733ef1dd944f53521e204b1a09430aa42e819e08092084edbd94` and `fd744e0c715ae1e4275c0b3f52bda1558486a2fc5e3f8c9d65dd421fd2a7c877`; the manifest records source, executable, input and cuDNN hashes but not all other dependency/runtime bytes.

A separate one-process screen at XSum's configured batch 32 completed on both runtimes, using two warmups and five measured batches. Rust/Python medians were 4,421.08/5,299.99 ms and peak process RSS was 1,057.64/1,866.04 MiB. All 6,400 codes and 1,536 IDs matched. Rust's CUDA pool used/reserved peaks were 2,201.24/2,912 MiB; Python's allocator allocated/reserved peaks were 3,489.83/5,504 MiB, again with different scopes. Raw outputs and `/usr/bin/time` records are under `reports/phase4-xsum-b32-screen-v1/`; this screen has only pre/post GPU snapshots and is not the required repeated batch-32 comparison. A subsequent [repeated batch-32 attempt failed when Python ran out of memory](b32-python-memory-v1.md); diagnosis found GPU-backed objects retained until garbage collection, so the prior Python allocator peaks are not the final fair reference.

The complete XSum Linux gate remains open: repeated batch-32 performance, official ROUGE quality, broader input parity, CFG and exact generator head-tie behavior still require work. No XSum MLX run is claimed.
