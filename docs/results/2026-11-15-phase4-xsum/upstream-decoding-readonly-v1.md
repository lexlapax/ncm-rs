# Read-only XSum decoding analysis

This is preparation only; XSum support, correctness, quality, and performance remain unimplemented and unqualified. The pinned upstream checkout is `c70274273f489abc73832b2b98584a8483b6b203`. Its `scripts/eval_shard.py` SHA-256 is `e1eb550123ec76601d1af9c59c2bb7a81d5ca683a662948fcb4d8164dd510c4a`; the XSum configuration SHA-256 is `5dee6b7339645a22362f695fbadb27df6e5254db2d3be0bff8516138d95da493`.

For the official XSum configuration, the context is 512 prefix positions and 48 generated positions, `query_level0` is enabled, and heads are tied to codebooks. The prefix pad ID is 50257. Before generation upstream masks prefix padding from attention; a raw embedding alone is insufficient. The official settings use temperature 1, top-k 1, top-p 0 and CFG 0. The upstream `_sample_level_raw` implementation still applies top-k thresholding, sorting/top-p and `torch.multinomial`; it is not simply a call to `argmax`. Ordinary unique-maximum cases may agree with greedy selection, but exact ties and RNG consumption need explicit qualification against the pinned implementation before substituting it. CFG's separate null branch is an additional supported-scope question even though this official setting is zero.

The final codec output path is also distinct from generator level selection. `pick_tokens` converts logits and the checkpoint's allowance distribution to FP64, scales the allowance by the output length, then processes output positions sequentially. At each step it subtracts a frequency penalty of 2.0 for excess counts, adds a deficit incentive with coefficient 1.0 and remaining-length factor, and applies adjacency penalties of 5.0 with a four-token window and 0.5 decay, in history order. It selects with `argmax`, updates counts and history, and only later cuts at EOS and removes EOS/PAD for decoding. Repeated prior tokens cause repeated adjacency updates; the operation order and first-index final argmax ties are material. The existing generic codec backend promises FP32 operations, and MLX does not expose GPU FP64, so silently performing these adjustments in FP32 would not reproduce this contract.

One possible exact-semantics baseline is an explicitly implemented, native Rust CPU final-selection step operating on the already-produced FP32 logits and FP32 allowance promoted to FP64. It would require carefully matching upstream's individual rounding and update order and testing against pinned PyTorch, including repeated history entries, ties and near-ties. It is a design candidate, not an implemented or qualified fallback. The inspected `inference.token_unigram` is a finite FP32 tensor of length 50,304. For the configured 32-by-48 batch this implies 309,067,776 bytes (294.75 MiB) of FP32 logits before any CPU workspace; one batch row is 9,658,368 bytes (9.21 MiB). The existing backend contract exposes `narrow` and `read_f32`, so row-chunked readback is a candidate to bound host workspace, but transfer, synchronization, and CPU scanning cost must be measured against the user-required Python latency and RSS direction. No device-to-host traffic or performance was measured in this analysis, and chunking does not remove the already existing device logits allocation.

Before implementation, also reconcile tied heads, nine levels, level-zero query generation, prefix masks and checkpoint tensor inventory with the existing Sudoku- and TinyStories-specific validators. Any candidate must pass Linux/CUDA correctness and quality first, then Metal, with the same explicit FP64 semantics or a separately reviewed alternative. No upstream pin, model algorithm, tolerance, device policy or production source was changed in this analysis.
