# XSum batch-32 Python memory investigation

The first repeated batch-32 comparison, `reports/phase4-xsum-cuda-performance-b32-v1/`, did not complete. The first Rust process completed 30 measured batches with a 4,471.16 ms median, 4,488.87 ms p95 and 1,062.01 MiB process peak RSS. The following Python process failed with CUDA out of memory while trying to allocate 392 MiB, with about 277 MiB free. The monitor recorded no Rust benchmark process during that Python window. This is a retained failed comparison; it cannot establish a repeated Rust/Python batch-32 result. Manifest, activity and Python stderr SHA-256 values are `9c0c530c41ac79d95cda8a3b74154668e7c48839d43dbd7639f64481aa74c7cd`, `3ffef7fab70f79d8b7847b4257fce43a256340b0ab506fb4971fc55ae4b0c9ef` and `645e0f3af0cc0f738d22688c47ae8e23cfabbe057da03f61b401b6430b6652dd`.

A separate same-input Python diagnostic without explicit collection completed 16 trials before another OOM. Its sampled live allocated GPU memory while batch locals were still in scope rose from 1,240,621,056 bytes after trial 0 to 4,179,868,160 bytes after trial 15. The retained source and stderr hashes are `6b5ab9ee6ef68f64e712bbe7cc91e2843911e19314590e5ceb8c8c55277dae3c` and `19e6ba92dce109ca9a15ee1fcf658ef9381578096c23ea75f18afe428c5caa3d`.

In a seven-trial follow-up, dropping the batch tensors and invoking Python garbage collection after each batch reduced live allocated memory from 920,629,248 to 724,793,344 bytes each time. Later collections reclaimed 50 objects per batch and had a 50.74 ms median duration; the specific reference cycles were not identified. All 32 code rows and output-ID rows matched the earlier successful short Python screen. This supports a retained Python-object cycle as the source of the growth, but does not establish a PyTorch allocator defect. The follow-up source, stderr and output hashes are `10e878db6b427dd2b3d02821aae45c337e9109374a7823fff93f8ddc8b6b79ad`, `79d165c2d2c0200a7a4a08cae41c360d9ca069448b792eef54db51efa88b26c5` and `a84b849581c2aab8dccbc3ca2a6ce5ae03749fcba3f2f0b523c7043cf93561cf`.

The Python reference benchmark now explicitly drops its per-batch latent list and can collect garbage and synchronize after each batch. The repeated benchmark runner selects this cleanup and records its duration separately from generation; reports must show the cleanup-inclusive figures as well as generation-only timings. This is a documented reference-harness fix, not an upstream NCM algorithm change or a device-policy change. The earlier batch-1/4 performance comparison did not use it; its Python GPU allocator peaks may include retained cyclic objects, so those device-memory figures must not be interpreted as the final fair reference. Repeat batch 1/4 and batch 32 with the documented cleanup before using the new comparison for acceptance.

`tools/reference/xsum_quality_generate.py` prepares resumable upstream quality batches using the same explicit between-batch collection, per-batch output integrity checks and saved CPU/CUDA RNG states. Its CPU-only integrity tests pass; it has not yet run on the GPU or generated quality data. No XSum quality or batch-32 repeated performance gate is claimed.
