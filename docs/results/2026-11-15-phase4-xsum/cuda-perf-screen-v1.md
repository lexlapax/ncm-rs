# XSum CUDA performance investigation

Short exploratory screens on the first real XSum passages show that the restricted Rust path uses less whole-process host memory than pinned Python but does not yet meet the user's speed requirement. These are not acceptance measurements: each cell is one fresh process with two warmups and five batches; no p95 or statistical conclusion is claimed. The compared work includes generation, the upstream-equivalent FP64 final-token penalties and host readback of codes and IDs, but excludes model load. `/usr/bin/time -v` records peak RSS for the whole process including load. The first 32 input prefixes are authenticated as described in the [correctness record](cuda-top1-v1.md).

| Screen | Batch | Rust median | Python median | Rust peak RSS | Python peak RSS |
| --- | ---: | ---: | ---: | ---: | ---: |
| Initial | 1 | 194.88 ms | 189.19 ms | 1,064.00 MiB | 1,858.89 MiB |
| Initial | 4 | 711.94 ms | 680.45 ms | 1,057.82 MiB | 1,860.72 MiB |
| After CPU selection changes | 1 | 192.24 ms | 189.15 ms | 1,058.00 MiB | 1,860.60 MiB |
| After CPU selection changes | 4 | 702.18 ms | 679.05 ms | 1,059.30 MiB | 1,858.84 MiB |

All code and final-ID outputs matched between Rust and Python in these screens. The initial screen used no extra synchronization; the later screen adds a synchronization after decoder execution for a rough timing breakdown, so cross-screen changes cannot be treated as isolated speedups. The Rust timing point also includes raw greedy-ID calculation before that boundary, which the Python boundary does not. In the later screen, median time after that boundary was 6.25/19.00 ms for Rust versus 5.31/8.05 ms for Python at batches 1/4; this includes selection and output readback. The current Rust path transfers FP32 decoder logits to the CPU, whereas Python applies the FP64 penalties on CUDA. A GPU implementation is an investigation, not an established fix.

The CPU change keeps the five best scores before applying adjacency penalties: at most four distinct IDs can receive these nonpositive penalties, so one of the five is unaffected and a lower score cannot win. It applies the original FP64 operations to candidate scores in the same order and explicitly preserves first-index ties. A full-scan comparison covers 96 generated cases with ties and repeated histories; the pinned upstream CPU/CUDA oracle tests still pass. Separate rows in chunks of up to four are processed concurrently, retaining row order; chunked and whole-batch outputs are tested. The change does not alter the declared upstream tolerance or output policy.

The final source passed `CUDA_COMPUTE_CAP=86 RUSTC_WRAPPER= tools/check.sh --cuda`, including the real-device selector test and 18 existing operator cases. No XSum MLX gate, quality gate or full performance/memory gate is claimed.

An isolated CUDA FP64 selection feasibility screen is retained in `reports/phase4-xsum-gpu-penalty-v1/`; neither candidate is integrated. A single-block-per-row prototype matched all 96 saved real-passage IDs but averaged 13.85 ms per 2-row kernel sequence. A tiled two-kernel-per-position prototype matched those IDs and averaged 1.64 ms in the same narrow event-timing screen; its timing excludes allocations and output readback. It also matched three existing upstream varied/tie/history fixtures and ten additional seeded CPU-oracle cases, including vocabulary sizes around 256 and 512. These few cases do not establish exhaustive FP64 parity or end-to-end improvement. Compilation ran concurrently, and neither candidate has a controlled activity record.
