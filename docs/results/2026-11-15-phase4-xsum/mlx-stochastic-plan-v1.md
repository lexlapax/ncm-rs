# XSum Metal stochastic sampling preparation

The initial Metal CLI supports top-1 CFG-0 generation and [matched Python CUDA on 32 real passages](mlx-cli-real-v1.md). This candidate enables CFG-0 seeded sampling through the already implemented request-local SplitMix64 and Metal categorical operation, while retaining the explicit CPU FP64 final-token selector. Positive CFG remains explicitly rejected on Metal. Other sampling settings remain unsupported. No upstream pin, RNG equivalence claim or numerical tolerance changes.

On strict CUDA, the new CPU-final seeded path and the existing device-final seeded path matched all 6,400 codes and 1,536 IDs on the retained 32 real passages at seed 42. Source output is `reports/phase4-xsum-mlx-stochastic-cuda-probe-v1.json`, SHA-256 `f9e9aa42b6bcd4b8fd405e50c9689b11f0f3871bf1ec69c0535ef29b2d2c7f08`. The reference was copied into a new Mac results directory and hash-verified. After Linux full CUDA validation, build the pushed Metal CLI and run `tools/bench/check_xsum_mlx_stochastic.py`: it compares the same 32 passages and supplied random stream, records code and ID differences before failing any exact mismatch, and confirms positive CFG remains rejected. The comparison is a diagnostic, not a claim that cross-device sampling must be bit-identical or a stochastic quality/performance gate. Any differences need investigation; the existing CUDA near-boundary exceptions remain visible.

Linux `tools/check.sh --cuda` subsequently passed, including 18 real CUDA operator cases (`reports/phase4-xsum-mlx-stochastic-linux-v1.log`). Strict-cuDNN Clippy on the backend and CLI also passed with warnings denied (`reports/phase4-xsum-mlx-stochastic-strict-clippy-v1.log`). These do not compile or qualify the Mac-only branch.
