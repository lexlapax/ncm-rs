# Rust structure and ownership audit — in progress

The declaration inventory is [rust-struct-declarations-v1.txt](rust-struct-declarations-v1.txt). It covers explicit Rust `struct` declarations in the workspace crates, examples/tests, and the vendored Tokenizers source; it is a source inventory, not a complete count of macro-generated types or an allocation measurement. Vendored upstream and non-Sudoku tokenizer structures are not part of the Phase 3 Sudoku hot path; their prior [Phase 2 performance comparisons](../2026-11-11-phase2-optimization/phase2-performance-summary-v2.md) remain applicable to those workloads only. No claim that every structure is globally optimal follows from this inventory.

| Structures / area | Time and space observations | Disposition |
| --- | --- | --- |
| `Generator`, `GeneratorWeights`, `GeneratorConfig`, generator `Envelope` | The initial implementation retained weights in a string-keyed tree and formatted names inside every block/level. The candidate consumes the checked map into typed `GeneratorParameters`, `GeneratorBlock` and `Affine` records at load, removing those per-request name allocations and map lookups without copying tensor storage. The initial implementation also recreated RoPE/masks per level and used separate Q/K/V materializations. | Fused split-half RoPE, packed Q/K/V, typed weights and 1,064,232 logical bytes of prepared per-level `LevelGeometry` are under numerical, time and memory evaluation. Specialized bit-exact CUDA layout copies are also under evaluation; unsupported shapes and pre-compute-7.5 devices use the generic device operation. The typed layout did not show a distinguishable batch-128 latency win in one exploratory comparison; its allocation and metadata effects are structural, not a claimed measured speedup. |
| `Generated`, `Decoded`, `Encoded`, `Codec` | `Decoded`/`Encoded` deliberately retain per-level snapshots for codec API semantics. The first generator reused that full API after already accumulating its latent, recomputing all levels and retaining 12 full-sized decoder snapshots. `Codec` owns immutable weights and bounded model-local codebook norm cells. | The generator candidate reuses its existing accumulated latent and returns codes/logits/IDs without retaining codec snapshots. Existing codec snapshot behavior is unchanged. Quality and hardware memory gates remain pending. |
| `Artifact`, `Manifest`, `FileRecord`, `TensorRecord`, `TensorDtype` | Checked loading retains owned bytes for all canonical payloads and hash/inventory metadata. This makes checked reads independent of later filesystem changes but is approximately the full artifact size in host memory. | The CLI and timing candidate drop the checked `Artifact` once model tensors have been uploaded. Peak loading memory and steady memory must be reported separately; integrity checks remain unchanged. |
| `CandleBackend`, `Prepared`, `Cache`, `Geometry` | Backend clones share the device but own separate resampling caches and fused-projection state. Geometry retains no activations and is bounded at 64 entries / 1 MiB logical metadata. CUDA allocator retention and driver memory exceed that logical count. | Preserve ownership/isolation. Measure duplicate workspace/cache cost before considering sharing; no unproven memory reduction is claimed. |
| `BoundedLt`, `Fused`, `Matrix`, `Desc`, `Pref`, `NoFusedAlgorithm` | The workspace is 2.5 MiB per initialized handle on the tested Ampere device; handle wrappers have deterministic destruction, and per-call descriptors incur setup work. Newer device capacity differs. | Preserve the Phase 2 audited limits and numerical behavior. Profile descriptor/setup cost and the multiple-backend case before changing native resources. |
| `MlxTensor`, `MlxBackend` | Array handles and stream ownership do not by themselves measure physical storage; lazy graph lifetime and Apple unified-memory active/cache/peak counters require real Metal measurement. | Apple validation is pending after Linux. Do not infer its memory footprint from Rust struct sizes or CUDA results. |
| `RawCodecConfig`, `CodecConfig`, `Levels`, `QuantizerConfig`, `Residual`, `Auxiliary`, `FineDrop` | Bounded owned configuration and level arrays are parsed and validated at load, not constructed for every tensor operation. | Retain explicit validation and shape bounds. |
| Model `Envelope`, `Tokenizer`, `PreTokenizer`, `Prefix`, `NoTrace` and visitor types | Envelope structures are temporary parsers; `Prefix` borrows an observer and `NoTrace` is zero-sized. | No evidence of material inference memory or latency costs. |
| `Vocabulary`, `ByteBpe`, `HexString`, tokenizer `Raw` | TinyStories uses a compact byte arena plus offsets and a merge map; temporary input uses borrowed `Cow` where possible. The ranked merge scan can be quadratic on long words, within its request bound. | Sudoku generation does not use these types. Preserve tokenizer semantics and prior Phase 2 measurements; investigate long-input algorithm changes separately with parity and measurements. |
| `TokenizerMetadata`, `TextTokenizer`, HF `Canonical`, `CanonicalBpe`, `CanonicalWordPiece`, `Kind` and visitors | Model/tokenizer metadata is held once; bounded serde visitors construct upstream HF model data. The boxed implementation keeps the enum small but does not make underlying vocabulary/trie/cache memory free. | Preserve the pinned dependency and previously qualified tokenizer behavior. No new text-workload improvement or memory result is claimed. |
| Vendored Tokenizers declarations | Upstream contains tokenizer/encoding/normalization, models, caches, regex/iterators, trainers, decoders, processors, serialization and test helpers. Some preserve original and normalized strings, offset maps, vocabulary/reverse maps or caches for API semantics. These are not exercised by the Sudoku tokenizer. | The declaration inventory includes them; per-type optimization assessment and new text-workload profiles are not complete. Do not silently alter vendored algorithms or infer their allocation cost from struct size. |
| Vendored `BPE`, `WordPiece`, `WordLevel`, `Unigram`, `Cache` | BPE and WordPiece keep forward and reverse vocabularies; BPE also keeps merge ranks and a cache. Unigram has a token map, scored vocabulary, trie and cache. Their `Clone` implementations duplicate model data; BPE and Unigram create a fresh cache. The common cache reserves up to its configured capacity and defaults to 10,000 entries, with long inputs excluded from caching. | These are concrete text-workload space and clone-cost candidates, not Sudoku costs. Changing representations, cache policy, or shared ownership requires text parity and fresh text-workload measurements. |
| Vendored `Encoding`, `NormalizedString`, `PreTokenizedString`, `AddedVocabulary`, `TokenizerImpl` | Encodings retain parallel token, ID, mask and offset vectors; normalized strings keep original and normalized text and per-byte alignment. Added vocabulary owns forward/reverse indices, ordered token lists and matching automata. The tokenizer owns the model and optional processing stages. | These allocations support upstream offsets, decoding and special-token semantics. A lean ID-only path may be useful, but needs measured evidence and explicit API/offset parity; no change is implied by structure size alone. |
| Vendored BPE `Word`/`Symbol`/`Merge`, Unigram `Lattice`/`Hypothesis`/`Node`/`Trie` | BPE keeps a vector of linked symbols and ranked heap entries for merge ordering. The alternative Unigram lattice uses reference-counted, interior-mutable nodes in multiple per-position vectors; its trie has a hash map per node and its iterator clones matching prefixes. | Arena indices or a more compact trie could reduce allocations, but would change upstream internals and require separate corpus, offset, tie and decoding parity measurements. These are not in Sudoku generation; no improvement is claimed. |
| Vendored trainers, builders, visitors, decoders, processors, pre-tokenizers, regex and iterator helpers | Builders and trainers retain configuration and sometimes large intermediate counts; visitor/tagged types are deserialization helpers, while decoder/processor sequences own their component lists. Regex and normalization helpers can own patterns or compiled state. | Training-only and load-only owners are not per-Sudoku-request costs. Keep upstream behavior and profile any text inference hot path before redesigning it. |
| Examples and tests (`Capture`, `Output`, `Stages`, `Events`, probe `Prepared`, mock `Counter`, `HostTensor`, `Case`, etc.) | Diagnostic buffers and retained trace outputs can dominate memory in their own processes but do not establish production inference cost. Test mocks are not runtime models. | Keep measurement scope explicit and never compare instrumented timings as uninstrumented acceptance data. |

The initial Linux CUDA [baseline](linux-baseline-timings-v1.json) measures synchronized Rust/Python generation with three fresh processes per batch and 30 timed calls after five warmups. One-second GPU activity samples and raw results remain local. Background desktop GPU processes were present, so that capture is evidence of the observed gap, not an idle-machine guarantee. The user requires improvement in both speed and memory; candidate measurements and broader struct review remain open.

The initial batch-32 CUPTI diagnostic found 3,927 GPU kernel records, including 732 `ucopy_f32` and 192 negation records. The optimized candidate's corresponding diagnostic had 2,313 kernels and 230 `ucopy_f32`; recorded kernel-duration sums were 570 ms and 452 ms respectively. These are one instrumented process per version and include initialization; activity durations may overlap and are not wall-clock acceptance results. The Python CUPTI injection produced no kernel records, so it cannot be used to attribute the cross-runtime gap. The optimized candidate still spent a summed 241 ms in 404 `ampere_sgemm_128x64_tn` records. Raw local captures and scripts are under `.reference/phase3-cupti/`.

A separate temporary host-side diagnostic counted 14,315 generator cuBLASLt heuristic calls across 35 batch-32 requests and 41.616 ms total inside selection, or roughly 1.19 ms per request. NVIDIA's [cuBLASLt documentation](https://docs.nvidia.com/cuda/cublas/index.html#heuristics-cache) recommends reusing matching heuristic results, but this measured cost is too small on its own to justify adding a new native cache. The profiling-only instrumentation was removed.

Two concurrent requests sharing one generator stalled in the NVIDIA driver. A bounded debugger capture showed one thread inside `cuModuleGetFunction` and another in a CUDA upload; retaining the two custom layout functions did not eliminate the stall, and a second capture showed Candle's ordinary GELU kernel lookup concurrent with another kernel launch. The shared generator now serializes requests, and the concurrent golden test completed successfully in 4.93 seconds. This serializes callback execution too; callbacks must not re-enter the same generator. It does not establish safety for multiple generators sharing a CUDA context, or for arbitrary outside CUDA work. Kernel handles retain their owning module and avoid repeated lookup; their performance effect has not yet been separately measured. Further runtime investigation remains warranted.

Remaining request-local host work includes formatting trace names even for `NoTrace`, and formatting codebook names for level lookups. These are bounded by the model's levels, unlike tensor activations. Their actual share of latency has not been measured; changing the trace interface or codec weight representation solely on this observation would not establish a meaningful win.
