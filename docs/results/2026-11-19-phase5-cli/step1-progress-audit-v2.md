## Subsequent steps, still open

Step 2 requires per-profile stage timing and process RSS/device peak at batch 1 and largest measured batch on CUDA then Metal, a published ranked bottleneck table, and user selection of one or two targets per GPU. Step 3 requires measured hypotheses, the stated repetition protocol and applicable output/quality/cache gates; changes without measured benefit are reverted. Step 4 requires the full requirement-to-evidence audit and, if applicable, approval for the optimization release. None of these is satisfied merely by the current exploratory screens.

For the immediate CUDA gate, an uncontended measurement window and sufficient native-peak coverage are still needed. XSum and LM1B model probes already expose scoped CUDA pool high-water counters; the [WMT14 diagnostic](cuda-wmt14-pool-diagnostic-v1.md) now does too. These are not whole-process device peaks, and CLI/native-library allocation coverage remains incomplete. The existing production lifecycle observer remains fail-closed with an unresolved startup observation race ([investigation](linux-lifecycle-env-investigation-v1.md)); a test-only marker is not a production barrier. Do not stop desktop applications or change machine policy without approval. No GPU or runtime change was made for this progress audit.
