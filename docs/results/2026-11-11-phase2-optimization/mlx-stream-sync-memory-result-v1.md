# MLX stream synchronization memory diagnostic

Three fresh processes per version compared the existing synchronous event wait with an additional `mlx_synchronize` on the same thread's default GPU stream after each resident-block evaluation. The regular backend and model were unchanged. For batch four, immediate active bytes were 69,702,948 in all event-only runs and 59,970,828 in all synchronized runs; both reached 59,970,832 after the following diagnostic barrier. The immediate reduction also appeared at batches one and two. All twelve scope rows and four snapshot stages are retained.

Available token/code/output ID and retained-latent hashes match; block float outputs and timing were not compared. Active bytes return to zero after model drop in all processes. Fourteen process activity samples and thermal observations were recorded; the Mac was not isolated. The diagnostic supports synchronization as a way to reach the observed settled state, but does not prove that earlier callback lifetimes were the sole cause or establish a 1.05 gate pass. It calls an already-pinned `mlx-sys` dependency only from the isolated diagnostic example, and changes no production code or dependency pin.
